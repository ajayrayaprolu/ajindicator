AJ v2 — Intelligent Trading Mode Architecture & Implementation Plan

Reference document — 11 September 2026

Core decision: Keep SCORE, AI, and AI+SMC. Keep Advanced Crypto, Safe/Swing/Scalper, OB/FVG/BOS/CHOCH/liquidity analysis, and market synchronization. Do not make all of these independent mandatory gates. Calculation modes calculate/adapt confidence; one canonical authorization layer decides TRADE/NO_TRADE.

1. Actual problem

The main problem is not merely that two parameter files exist. The real problem is that the platform does not yet make the complete decision path sufficiently visible:

Which calculation mode produced the score, which conditions contributed, which threshold applied, and exactly why did the trade pass or fail?

The current practical workflow has become SCORE + development/reduced thresholds because production often gives NO_TRADE and AI/AI+SMC can become too restrictive. The new design must remove that uncertainty.

The system should support two ways to choose calculation mode:

  • AUTO / INTELLIGENT (default): the system observes market conditions and selects the appropriate calculation behavior.
  • EXPLICIT MANUAL: the user can force SCORE, AI, or AI+SMC from Indicator Settings.

3. Mode semantics

SCORE — normal/default market operation

SCORE is the normal opportunity engine. It should use weighted evidence from trend, momentum, volume, price action, structure, order flow, VWAP/CVD, liquidity, synchronization, and risk rather than requiring every institutional condition simultaneously.

market evidence
→ weighted score
→ score/risk validation
→ authorization

AI — adaptive protection

AI should not mean SCORE plus many mandatory conditions. It should adapt confidence and risk based on volatility, conflicting signals, abnormal conditions, and trap-like behavior.

base score
→ AI contextual adjustment
→ risk/trap adjustment
→ final confidence
→ authorization

AI + SMC — institutional/trap/reversal protection

AI+SMC adds contextual interpretation of OB, FVG, BOS, CHOCH, liquidity sweep and related institutional evidence. These should generally be evidence and modifiers, not a requirement that every engine returns YES.

base score
→ AI adjustment
→ SMC structural/liquidity adjustment
→ reversal/trap adjustment
→ final confidence
→ authorization

4. Intelligent automatic mode selection

This is the key clarification: the normal/default system should not require the user to watch the market and manually change modes.

Detected regimePreferred behaviorPurpose
Clean/normal trendSCOREMore valid opportunities without unnecessary institutional over-gating.
Elevated volatility / conflicting conditionsAIAdaptive confidence and risk protection.
Reversal / manipulation / institutional-risk conditionsAI+SMCUse OB/FVG/BOS/CHOCH/liquidity context to avoid traps and analyze structured reversals.

Debug output should show both Requested Mode (AUTO or explicit) and Effective Mode (SCORE, AI, or AI_SMC).

Manual override: if the user explicitly selects SCORE, AI, or AI_SMC, AUTO must not silently replace that selection.

5. Advanced Crypto

Advanced Crypto is a market-profile/calculation modifier, not a fourth trading mode.

Environment:       DEVELOPMENT / PRODUCTION
Mode:              AUTO / SCORE / AI / AI_SMC
Market Profile:    NORMAL / ADVANCED_CRYPTO
Strategy Profile:  SAFE / SWING / SCALPER

Advanced Crypto can alter calculation weighting/behavior for the supported crypto/gold/forex-style markets without duplicating authorization logic.

6. Safe / Swing / Scalper

ProfileIntent
SAFEHighest quality requirement, stronger risk/trap protection, fewer but safer trades.
SWINGBalanced confidence and risk requirements.
SCALPERMore opportunity-oriented; momentum, volume, spread and fast price action receive greater importance.

Profiles should modify weights/thresholds/aggressiveness, not create separate calculation engines or duplicate authorization gates.

7. Market synchronization — NIFTY/BANKNIFTY and BTC/SPX500

The synchronization feature must be inspected in the existing code before its exact semantics are changed. It exists as Indicator Settings toggles, but its runtime behavior and debug visibility have not yet been established.

Do not assume synchronization is mandatory or merely a confidence modifier until the current implementation is traced.

  1. Locate the sync toggle definitions and runtime consumers.
  2. Verify that attach/detach state reaches runtime calculations.
  3. Verify NIFTY/BANKNIFTY and BTC/SPX500 behavior separately where applicable.
  4. Expose sync status, direction, mismatch, attached/detached state and contribution in diagnostics.
  5. Preserve the existing intended behavior unless inspection proves it is incorrect.

Only after this audit should the exact role be classified as a modifier, filter, or hard safety gate.

8. OB / FVG / BOS / CHOCH / Liquidity

  • OB: institutional evidence; repeated reactions can strengthen confidence.
  • FVG: contextual imbalance/evidence, not automatically mandatory on every trade.
  • BOS: continuation confirmation.
  • CHOCH: potential regime/reversal warning; contextual rather than a simple checkbox.
  • Liquidity Sweep: contextual. A sweep followed by rejection/CHOCH/OB/FVG is different from a sweep followed by continuation.
  • Repeated OB/FVG reactions: useful evidence; three respects can be stronger than one without becoming a universal mandatory gate.

10. DEV vs PROD

Development remains available but is not the normal trading mode.

DEV purpose: test whether the same calculation pipeline can produce a candidate trade when authorization thresholds are relaxed.

PRODUCTION:
same calculation
→ normal threshold
→ TRADE / NO_TRADE

DEVELOPMENT:
same calculation
→ relaxed test threshold
→ TRADE / NO_TRADE
DEV must never be the default. It is a validation/diagnostic/testing facility, not the normal production strategy.

11. Why current 25/60 and 36/60 results matter

A result such as 25/60 or 36/60 does not prove that 60 is simply too high. It means the calculation is producing a low result and/or another gate is contributing to the rejection.

  • Inspect score component weights.
  • Inspect conditions that zero or heavily penalize scores.
  • Inspect structure and institutional-confluence behavior.
  • Inspect risk qualification.
  • Inspect order-flow interpretation.
  • Inspect FVG/OB availability.
  • Inspect synchronization behavior.
  • Inspect downstream authority/execution gates.
  • Verify that DEV thresholds are actually applied where expected.

12. Canonical configuration

Use src/runtime/config/RuntimeParameters.ts as the canonical runtime configuration surface, while initially retaining src/indicators/AJIndicator/config/AJRuntimeParameters.ts during migration.

Do not immediately delete the second file. First identify every consumer and migrate safely.

19. Next implementation plan — exact sequence

Step 1 — Freeze current behavior

  • Do not change the main calculation engines yet.
  • Do not lower production thresholds yet.
  • Do not delete either parameter file.
  • Keep current behavior as the baseline.

Step 2 — Audit both parameter files

  • Compare every field in both files.
  • Classify each field as calculation parameter, threshold, risk parameter, mode flag, market profile, strategy profile, or UI/runtime state.
  • Identify duplicate and conflicting values.

Step 3 — Find every AJRuntimeParameters consumer

Search the source tree and create a complete migration list. Do not replace imports blindly.

Step 4 — Verify current mode flow

Indicator Settings
→ selected mode
→ RuntimeParameters
→ AJRuntimeContext
→ calculation engine
→ decision engine
→ execution
→ dashboard/debug

Confirm SCORE, AI and AI_SMC toggles actually change runtime behavior.

Step 5 — Verify synchronization

Trace the NIFTY/BANKNIFTY and BTC/SPX500 synchronization toggles from Indicator Settings into runtime. Determine whether attach/detach is operational and where its result is consumed.

Step 6 — Add explicit configuration dimensions to RuntimeParameters

environment
requestedMode
effectiveMode
marketProfile
strategyProfile

Keep compatibility fields during migration.

Step 7 — Add AUTO mode

Implement a selector that produces an effective mode from observable market context. Explicit SCORE/AI/AI_SMC selection bypasses AUTO.

Step 8 — Add profile-based parameter selection

Move threshold/profile selection into the canonical parameter layer. Strategy and market profile may select different values while existing calculation logic remains intact.

Step 9 — Add one structured authorization result

Centralize the final authorization around the normalized calculated result. Do not duplicate calculations in the gate.

Step 10 — Preserve hard safety blockers

Conditions such as invalid execution/risk states may remain hard blockers. Their classification must be based on the existing implementation during inspection.

Step 11 — Add decision diagnostics

Expose requested/effective mode, environment, market profile, strategy profile, regime, base score, AI/SMC adjustments, final confidence, thresholds, sync state, OB/FVG/BOS/CHOCH/liquidity evidence, risk/execution results and primary blockers.

Step 12 — Test DEV correctly

Use DEVELOPMENT only to establish whether candidate trades exist below production thresholds. The same calculation path must be used. Record calculated score versus applied threshold.

Step 13 — Test AUTO in production simulation

Run AUTO diagnostically across clean trend, high volatility, low volume, trend/momentum conflict, reversal, liquidity sweep, OB/FVG reaction, BOS, CHOCH, sync aligned and sync mismatched conditions.

Step 14 — Tune production thresholds from evidence

Only after diagnostics are reliable should thresholds be tuned. The objective is controlled improvement in valid opportunities while preserving safety and avoiding obvious traps.

Step 15 — Migrate AJRuntimeParameters

After all consumers are migrated and tests are clean, reduce it to a compatibility/deprecation layer or remove it.

20. What we should NOT do

  • Do not blindly reduce every threshold to make trades appear.
  • Do not make FVG + OB + BOS + CHOCH + liquidity sweep mandatory for every trade.
  • Do not make AI a duplicate SCORE engine with extra hard gates.
  • Do not make Advanced Crypto a fourth trading mode.
  • Do not create separate authorization systems for SCORE, AI and AI+SMC.
  • Do not remove existing engines merely to simplify configuration.
  • Do not change main calculation files until the current flow is mapped.
  • Do not delete AJRuntimeParameters until all consumers are migrated.

21. Final operating philosophy

The system should become intelligent by selecting the calculation depth, not by randomly lowering thresholds.

Normal market → SCORE gives efficient opportunities.

Unstable/high-volatility market → AI becomes more protective.

Reversal/trap/institutional-risk market → AI+SMC becomes more protective and context-aware.

All three ultimately pass through one transparent authorization decision.

22. Immediate next coding action

Before modifying thresholds, the first coding task is an audit of the two parameter files and all consumers. Then make the smallest possible changes inside the two requested files, while leaving existing calculation engines untouched unless an import/compatibility redirect is required.

Target: one canonical runtime configuration, intelligent AUTO mode by default, explicit manual override when requested, DEVELOPMENT only for testing, and complete decision diagnostics.

This document is an implementation reference. It intentionally separates architecture from code changes so existing AJ v2 calculation engines can be preserved during migration.
