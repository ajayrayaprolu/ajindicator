AJPlatformDecoupledMigration

Project purpose, target architecture, migration strategy, multi-OpenAlgo orchestration, compatibility model, validation gates, and the surgical dependency-ordering design used by the migration script.

1. Why this project exists

The authoritative AJInstitutional source currently lives under C:\AI-Institutional\src. The project is creating a repeatable migration/orchestration mechanism that can deploy that AJ source into multiple independently installed OpenAlgo frontends under C:\AJMultiAlgo.

The central objective is decoupling AJInstitutional from the OpenAlgo platform implementation. AJ remains the calculation/decision engine. OpenAlgo remains the broker/platform/UI host. The migration script creates the thin adapter boundary between them.

AJInstitutional Core
Authoritative trading/indicator calculation engine. Broker and UI agnostic.
AJ OpenAlgo Adapter
Converts OpenAlgo bars/context into AJ inputs and AJ results into the chart/indicator contract.
AJ Indicator Orchestrator
Lifecycle, cache, incremental/tail calculation, registry and worker-oriented orchestration.
AJ UI/Consumers
Dashboard, debug and advisory consumers of shared AJ state; not the calculation authority.

4. Why the migration script is required

There are multiple OpenAlgo installations with potentially different destination versions and broker adapters. A manual copy is unsafe because platform files and module contracts can differ between installations.

  • Discover all OpenAlgo instances below C:\AJMultiAlgo.
  • Use C:\AI-Institutional\src as the authoritative AJ source.
  • Extract the reachable AJ source/import closure into each destination's frontend/src/indicators/AJInstitutional.
  • Create destination-local AJ package structure without requiring AJ packages outside that boundary.
  • Preserve the destination OpenAlgo platform files.
  • Detect the destination's actual OpenAlgo Charts/indicator registration contract.
  • Generate only the thin bridge required by that destination contract.
  • Run import, TypeScript and full frontend build gates before reporting success.

7. Migration lifecycle implemented by the script

  1. Discover: scan the multi-instance root and identify OpenAlgo frontends.
  2. Resolve destination: establish the canonical AJ destination.
  3. Backup: back up destination-native frontend wiring files before AJ bridge changes.
  4. Source preflight: walk the authoritative AJ import closure and identify unresolved/third-party dependencies before copying.
  5. Extract: copy the reachable AJ Core source closure into the destination-local AJ package boundary.
  6. Generate adapters: create AJ runtime/context/result/orchestration adapters locally.
  7. Normalize: repair only AJ-owned aliases/imports; do not rewrite OpenAlgo platform code.
  8. Restore destination dependencies: use the destination's own package manifest/lockfile when required.
  9. Detect compatibility: inspect the actual installed openalgo-charts contract.
  10. Generate thin registration: select the correct root, indicators-tier, or legacy host bridge.
  11. Wire terminal: add the destination-local AJ registration import to the native terminal loader.
  12. Audit: verify AJ boundary and local import closure.
  13. Build: run TypeScript preflight and the destination's actual frontend build.
  14. Report: only report deployment complete after all required gates pass.

8. Critical compatibility model

The destination version is not assumed. The script detects what is actually installed.

native-root
registerIndicator is exported by the root OpenAlgo Charts module.
native-indicators-tier
registerIndicator is exported by openalgo-charts/indicators.
legacy-host
The destination frontend exposes an older host registration pattern; the AJ bridge uses the host API rather than assuming the current Charts API.
unsupported
No safe registration contract is detected. The script stops rather than changing the destination platform.

9. Dependency-ordering design

Failure that triggered the v8 surgical correction: v7 attempted to inspect node_modules/openalgo-charts/package.json from New-CoreAdapters before destination dependencies were guaranteed to exist. A fresh or partially installed frontend therefore failed even though its AJ source extraction was successful.

The corrected sequence is:

destination selected
    ↓
backup destination-native wiring
    ↓
restore/check destination TypeScript toolchain
    ↓
restore/check destination-native openalgo-charts dependency
    ↓
AJ source preflight + extraction
    ↓
AJ adapter generation  ← no platform compatibility inspection here
    ↓
AJ import normalization
    ↓
compatibility detection against actual installed destination package
    ↓
thin register.ts generation
    ↓
native terminal loader wiring
    ↓
import closure / TypeScript / full build

This specifically covers old OpenAlgo destinations, new OpenAlgo destinations, fresh node_modules, and partially installed node_modules without copying Fyers platform files or intentionally changing OpenAlgo versions.

10. Why the script must not copy old Fyers platform files

A prior build demonstrated the risk: old Fyers frontend files introduced incompatible destination types such as drawing document/index signatures, legend properties, drawing style properties and Trading component props. Those failures were platform-contract mismatches rather than AJ calculation failures.

Therefore the current design backs up and preserves destination-native files such as:

  • package.json
  • package-lock.json
  • ChartPane.tsx
  • IndicatorSettingsDialog.tsx
  • PlotStyleRow.tsx
  • chartTypes.tsx
  • chartTheme.ts
  • terminal.ts

The only intended platform-side integration is a destination-local AJ loader import.

11. AJ indicator descriptor

The generated AJ module exposes the chart-facing descriptor through the adapter layer. The known descriptor responsibilities include:

calc
Full/history calculation and AJ output storage.
calcTail
Incremental/tail calculation and latest-output storage.
markers
AJ marker output for chart consumers.
draws
AJ drawing/zone output for chart consumers.
table
Latest dashboard/table data exposed to the chart layer.

12. Incremental calculation and state

The architecture is intended to avoid recalculating expensive history unnecessarily. AJ state and outputs are retained in destination-local orchestration storage, allowing full history and tail/incremental execution paths.

The migration script's role is not to invent the trading logic. It packages and wires the existing authoritative AJ implementation into the destination contract.

14. Error handling philosophy

  • Every deployment step is explicit and logged.
  • Errors include function, script line and stack information.
  • No success is reported after a failed audit/build.
  • The script does not silently downgrade/upgrade OpenAlgo to match a legacy reference.
  • Automatic repairs are restricted to deterministic AJ-owned/generated artifacts and destination dependency restoration.
  • Platform-contract uncertainty causes a controlled stop instead of speculative source copying.

15. Current surgical revision

The v8 revision removes the dependency-sensitive compatibility lookup from New-CoreAdapters. New-CoreAdapters now performs only AJ adapter generation. Compatibility detection is performed later, after destination dependencies are guaranteed.

17. Project success criteria

  • AJInstitutional source remains authoritative and broker/platform agnostic.
  • Each OpenAlgo instance retains its own native platform implementation.
  • No old Fyers platform snapshot is copied into a new destination.
  • Old and new destination registration contracts are detected rather than assumed.
  • Fresh and partially installed dependency states are handled deterministically.
  • AJ artifacts remain inside each instance's frontend/src/indicators/AJInstitutional boundary.
  • Incremental/tail execution remains available through the AJ orchestration layer.
  • Build success is required before deployment success is reported.
