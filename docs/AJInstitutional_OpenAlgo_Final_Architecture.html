1. Executive architecture decision

The recommended architecture is to separate AJInstitutional business logic from OpenAlgo integration and from OpenAlgo UI rendering. AJInstitutional becomes a reusable package that consumes a canonical candle/runtime contract and produces a canonical indicator-result contract. A single generic OpenAlgo adapter/orchestrator then connects that package to any OpenAlgo instance.

Core decision: Do not copy the original AJMultiAlgo application into every OpenAlgo instance. Do not create a new 30–40 KB monolithic registration file for every indicator. Instead, build one reusable AJ platform consisting of:
  • AJInstitutional Core — broker- and UI-independent calculation engine.
  • AJ OpenAlgo Adapter — translates OpenAlgo chart data into AJ contracts and AJ results into OpenAlgo chart primitives.
  • AJ Indicator Orchestrator — one generic lifecycle/registration/cache layer shared by all AJ indicators.
  • AJ UI package — dashboard, debug, advisory and zone-inspection components that consume engine state.
  • Thin indicator manifests/factories — metadata and factory definitions, not business logic.
1generic OpenAlgo integration/orchestration layer
NAJ indicator packages can be installed through the same mechanism
1AJ core version can serve Fyers, IndStocks and other OpenAlgo instances

OpenAlgo is currently structured as a self-hosted Flask + React platform with broker plugins, while the OpenAlgo Charts project uses a descriptor/registry-oriented chart architecture. This makes a thin adapter + descriptor approach a natural fit rather than embedding AJ logic into the chart core. OpenAlgo repository and OpenAlgo Charts.

2. Objectives and non-goals

2.1 Objectives

  • Run the same AJInstitutional indicator on every OpenAlgo instance.
  • Allow Fyers, IndStocks, AliceBlue and future brokers to use the same AJ source package.
  • Use OpenAlgo as the broker/data boundary rather than maintaining broker API logic inside AJInstitutional.
  • Use OpenAlgo's own chart frontend as the visualization surface.
  • Preserve AJ plots, markers, zones, dashboard information, debug information and advisory output where practical.
  • Remove unnecessary duplication of the original AJMultiAlgo application.
  • Make adding another indicator a package/manifest operation instead of rewriting an OpenAlgo integration.
  • Improve responsiveness by moving expensive calculation away from the chart's synchronous UI path.
  • Make indicator output deterministic and testable independently of broker.

2.2 Non-goals

  • Do not port the complete AJMultiAlgo frontend/backend.
  • Do not maintain a second chart engine such as a separate TradingView/lightweight-charts rendering stack for the OpenAlgo implementation.
  • Do not embed broker credentials, broker APIs or broker-specific WebSocket logic in AJInstitutional Core.
  • Do not make the AJ engine depend on React, DOM, canvas or OpenAlgo chart objects.
  • Do not force a single OpenAlgo installation to become a multi-broker router.

3. Current-state assessment

The current migration uses an OpenAlgo frontend with an AJInstitutional subtree containing the migrated AJ runtime, core modules, UI, dashboard, debug, zones, services and a large register.ts integration adapter.

3.1 What the current registration layer is doing

The current registration approach is conceptually valid because OpenAlgo needs a descriptor/registration boundary. However, the registration file should be treated as an adapter boundary, not as the home of the indicator's business logic.

The current pattern performs historical calculations by iterating through bars, building runtime contexts and executing the AJ pipeline. The important architectural issue is that the chart calculation path is synchronous and repeatedly constructs growing candle prefixes. For a dataset of n bars, repeatedly executing slice(0, index + 1) alone creates O(n²) array-copy work before considering the indicator engine itself.

Important: Splitting a large register.ts into smaller files will improve maintainability, but it will not by itself solve chart lag. The calculation model must also become incremental and preferably run in a Web Worker for expensive historical/replay processing.

4. Architecture constraints

  1. One OpenAlgo instance = one active broker deployment. The same AJ package must therefore be broker-neutral and reusable across instances.
  2. OpenAlgo owns broker connectivity. The AJ indicator should consume normalized chart bars and context rather than call Fyers/IndStocks/AliceBlue APIs directly.
  3. OpenAlgo Charts owns rendering. AJ should produce plots, markers and drawing descriptors rather than recreate the charting engine.
  4. OpenAlgo custom indicators have a registration contract. Therefore registration cannot be eliminated; it must be centralized and made generic.
  5. AJ calculation may be computationally expensive. Historical calculations must be incremental/cached and should be moved off the browser main thread when they can block interaction.
  6. AJ output contains more than a single line. The architecture must support plots, markers, zones, tables, dashboard state, debug state and advisory information.
  7. New broker instances must not require AJ source changes.

5.1 Architectural flow

  1. OpenAlgo obtains historical and live market data through its configured broker integration.
  2. OpenAlgo chart data is passed to the generic AJ OpenAlgo Adapter.
  3. The adapter converts OpenAlgo bars into the canonical AJBar representation.
  4. The orchestrator owns an AJ engine instance for the chart/indicator context.
  5. The AJ Core executes the domain logic.
  6. The core emits an AJIndicatorResult.
  7. The result adapter converts the result into OpenAlgo plot/marker/draw/table descriptors.
  8. OpenAlgo Charts renders those primitives.
  9. Dashboard/debug/advisory components subscribe to the same AJ state/result stream and do not independently recalculate the indicator.

7.1 Preferred dependency model

Each OpenAlgo instance should depend on the shared packages rather than containing copied AJ source.

{
  "dependencies": {
    "@ajmulti/aj-institutional-core": "workspace:*",
    "@ajmulti/aj-openalgo": "workspace:*",
    "@ajmulti/aj-ui": "workspace:*"
  }
}

If a single workspace cannot be used across the repositories, publish the packages to a private npm registry or consume versioned tarballs/Git packages. The architectural principle is unchanged: one source of truth for AJ Core.

export interface AJIndicatorResult {
  time: number;

  markers?: AJMarker[];

8.5 Design principle

The core should never return OpenAlgo-specific objects such as SeriesMarker or chart renderer instances. Those belong to AJResultAdapter. This keeps the core testable and portable.

9. AJ Indicator Orchestrator

The orchestrator is the central component that eliminates repeated custom integration work.

9.1 Responsibilities

  • Discover installed AJ indicator modules.
  • Validate indicator manifests.
  • Create one engine/runtime instance per chart/indicator context.
  • Manage history calculation.
  • Process incremental live updates.
  • Cache results/state.
  • Coordinate Web Worker execution when enabled.
  • Convert results into chart-facing descriptors.
  • Notify dashboard/debug/advisory subscribers.
  • Destroy and clean up engine state when a chart is removed.

9.2 Generic interface

export interface AJIndicatorModule {
  manifest: AJIndicatorManifest;

  createEngine(settings?: AJSettings): AJRuntimeEngine;

  createAdapter(): AJOpenAlgoAdapter;

  createUI?(): AJIndicatorUI;
}

export interface AJIndicatorManifest {
  id: string;
  version: string;
  engine: string;
  capabilities: string[];
}

9.3 Orchestrator API

export interface AJIndicatorOrchestrator {
  registerPackage(module: AJIndicatorModule): void;

  initialize(
    chartId: string,
    instrument: AJInstrumentContext,
    settings: AJSettings
  ): AJIndicatorSession;

  calculateHistory(
    sessionId: string,
    bars: readonly OpenAlgoBar[]
  ): Promise<AJIndicatorResult[]>;

  update(
    sessionId: string,
    bar: OpenAlgoBar
  ): Promise<AJIndicatorResult>;

  snapshot(sessionId: string): AJIndicatorSnapshot;

  destroy(sessionId: string): void;
}

10. Registration and OpenAlgo integration

OpenAlgo Charts uses a descriptor/registry model. Its documentation explicitly describes indicators as registered descriptors and states that adding a custom indicator is a registration rather than a core-chart switch. This is directly compatible with the proposed architecture. OpenAlgo Charts README.

10.1 What replaces the current large register.ts

The recommended future registration path is a thin generic bridge. It may still be called a registration module because OpenAlgo requires registration, but it contains almost no business logic.

import {
  registerAJPackages
} from "@ajmulti/aj-openalgo";

import {
  AJInstitutionalModule
} from "@ajmulti/aj-indicators";

export default function register(api) {
  registerAJPackages(api, [
    AJInstitutionalModule
  ]);
}

The OpenAlgo bridge owns the registration contract. AJInstitutional owns its manifest and engine factory. A new indicator is added to the catalog; the bridge itself does not change.

10.2 Manifest example

export const AJInstitutionalManifest = {
  id: "AJInstitutional",
  version: "1.0.0",
  engine: "aj-institutional",
  adapter: "openalgo",
  capabilities: [
    "overlay",
    "markers",
    "zones",
    "table",
    "dashboard",
    "debug",
    "advisory"
  ]
};

10.3 Architectural rule

The registration boundary is a platform contract, not an indicator implementation. A registration file may remain because OpenAlgo requires it; what must disappear is the large amount of calculation, state construction and visualization mapping currently embedded in that file.

11.2 Live candle/tick update

new/changed OpenAlgo bar
        ↓
AJBarAdapter
        ↓
engine.update(bar)
        ↓
incremental state transition
        ↓
one AJIndicatorResult
        ↓
chart series/marker/zone update

11.3 Recommended engine contract

engine.initialize(history);
engine.calculateHistory(history);  // once
engine.update(bar);                 // incremental
engine.snapshot();                  // current state
engine.reset();                     // symbol/timeframe/settings change

The goal is to avoid reconstructing the complete historical prefix for every bar and to avoid creating a fresh engine for each calculation step.

12. Performance and UI responsiveness

Performance priority: The largest likely cause of the reported mouse/crosshair/candle delay is not simply the size of the registration file. It is the synchronous calculation model, repeated prefix-array construction and potentially repeated full pipeline work on the chart thread.

12.1 Problems to remove

Anti-patternReplacement
candles.slice(0, index + 1) inside every historical iterationPersistent history/state; pass index/window references or immutable shared history.
New RuntimeEngine for each barOne engine per indicator/chart session.
Full recompute for every tickIncremental update(bar).
Dashboard reruns calculationDashboard subscribes to result/state.
Debug UI reruns calculationDebug UI consumes emitted events/snapshots.
Large synchronous historical runWeb Worker for heavy calculation.
Full result arrays sent to chart on every tickSend only changed result/delta where chart API permits.

12.2 Web Worker model

Main UI thread
    │
    ├── OpenAlgo Chart
    ├── Crosshair / mouse
    ├── React dashboard
    │
    └── AJ Worker Client
             │
             │ postMessage()
             ▼
        AJ Indicator Worker
             │
             ├── RuntimeEngine
             ├── historical calculation
             ├── incremental update
             └── state cache
             │
             │ postMessage(result/delta)
             ▼
        AJ Worker Client
             │
             ├── Chart result adapter
             └── UI state store

12.3 Performance acceptance targets

  • Initial historical calculation may take longer, but it must not freeze the main UI thread for the full duration.
  • Live update processing should be incremental.
  • Crosshair movement must remain responsive during AJ calculation.
  • Chart rendering must not repeatedly receive complete historical datasets when only the last bar changed.
  • Multiple charts must maintain isolated AJ sessions.
  • Engine state must be explicitly destroyed when a chart is removed.

12.4 OpenAlgo chart compatibility

OpenAlgo Charts is designed around a canvas rendering pipeline, indexed data and live updates. Its architecture explicitly emphasizes cheap cursor/crosshair repainting and live candle updates. The AJ integration should therefore feed the chart with native series/marker/drawing primitives rather than introduce another DOM-heavy rendering layer. OpenAlgo Charts architecture.

13.2 Important rule

The original AJ dashboard/debug/advisory components can be reused selectively, but they must become consumers of AJ state. They must not instantiate a second chart/data engine or independently calculate the indicator.

13.3 Why OpenAlgo should remain the chart engine

OpenAlgo Charts already supports custom indicators and a registry-oriented extension model. The architecture describes indicator descriptors, lifecycle ownership and live update behavior. Reusing it avoids duplicated interaction state, time scales, crosshair logic and chart rendering. OpenAlgo Charts indicator documentation.

14.1 Broker independence

There should be no code such as:

if (broker === "fyers") { ... }
else if (broker === "indstocks") { ... }

Instead:

OpenAlgoDataSource
       ↓
AJOpenAlgoAdapter
       ↓
AJCore

Broker-specific differences belong at the OpenAlgo boundary. The AJ engine receives the same canonical contract regardless of the broker instance.

14.2 Golden broker-independence test

Feed the same canonical candle sequence into the AJ Core from Fyers and IndStocks adapters. The AJ result must be identical apart from explicitly documented feed differences such as missing/late bars.

15.4 New broker deployment

  1. Create/clone an OpenAlgo instance.
  2. Configure the broker plugin and credentials according to OpenAlgo's broker model.
  3. Install the same AJ package versions.
  4. Enable the generic AJ indicator bridge.
  5. Open the chart and verify the indicator.

No AJ source changes should be required.

OpenAlgo's broker documentation describes broker adapters as plugin directories and states that an OpenAlgo instance uses one configured broker at a time. This reinforces the decision to keep broker concerns outside AJ Core. OpenAlgo broker connection documentation.

16. Migration plan from the current code

Phase 1 — Freeze the working implementation

  • Do not delete the current register.ts.
  • Tag the current working version.
  • Capture screenshots and golden output for known symbols/timeframes.

Phase 2 — Build the dependency graph

Start from the actual AJ runtime entry points such as RuntimeEngine, decision engine, result types and indicator calculations. Follow TypeScript imports to determine the required closure.

Phase 3 — Extract AJ Core

  • Move pure calculation modules into aj-institutional-core.
  • Remove React/OpenAlgo imports.
  • Remove broker services.
  • Remove old chart rendering dependencies.
  • Preserve algorithm behavior exactly.

Phase 4 — Create canonical contracts

  • AJBar
  • AJInstrumentContext
  • AJRuntimeContext
  • AJIndicatorResult
  • AJ settings/state types

Phase 5 — Create OpenAlgo adapter

  • Bar conversion.
  • Context construction.
  • Result mapping.
  • Plot/marker/zone mapping.

Phase 6 — Create orchestrator

  • Session lifecycle.
  • Engine caching.
  • Incremental updates.
  • Registry/catalog.
  • Cleanup.

Phase 7 — Refactor register.ts into compatibility mode

The current registration module should delegate to the new orchestrator. Once the new path is proven, the old large implementation can be retired.

Phase 8 — Add Web Worker

Move expensive historical/replay calculations into the worker while keeping the chart and UI on the main thread.

Phase 9 — Extract UI

Convert dashboard/debug/advisory/zone views into state consumers.

Phase 10 — Install into second OpenAlgo instance

Install the exact same AJ package into the IndStocks OpenAlgo instance. Only broker/OpenAlgo configuration should differ.

Phase 11 — Build the reusable base

Once Fyers and IndStocks both work from the same package, freeze the generic bridge as the standard AJ/OpenAlgo integration layer for future instances.

17. How to select only the required AJ source files

Do not copy the AJInstitutional directory wholesale. Build the required set using an import/dependency graph.

17.1 Keep if it is pure domain/runtime logic

  • Runtime engine and runtime context.
  • Decision engine.
  • Signal generation.
  • Lifecycle state.
  • Confidence/scoring logic.
  • Risk/execution calculations that do not call a broker.
  • Zone calculations.
  • Indicator calculations.
  • AJ-specific types and configuration.
  • Pure utilities referenced by the above.

17.2 Exclude by default

  • Broker clients.
  • Broker authentication.
  • Original WebSocket infrastructure.
  • Original data-feed adapters.
  • Original chart renderer.
  • TradingView/lightweight chart wrappers.
  • Application-level routing.
  • Original authentication pages.
  • Original app shell.
  • Pages/layouts unrelated to the OpenAlgo extension.
  • Duplicate state stores that exist only for the old application shell.

17.3 Automated extraction is recommended

For maintainability, create a small tooling command that starts from declared entry points and traverses local imports:

AJ Core entry points
        ↓
TypeScript import graph
        ↓
reachable source files
        ↓
dependency classification
        ↓
core package

This prevents accidental copying of the entire original application and makes future AJ indicator extraction repeatable.

  • Verify no unbounded event-listener accumulation.

18.4 Acceptance condition

The architecture is considered successful when the same AJ package can be installed into Fyers OpenAlgo and IndStocks OpenAlgo without modifying AJ Core and produces equivalent results for equivalent candle input.

19. Security and operational boundaries

  • AJ Core must never receive broker API secrets.
  • AJ Core should not directly call broker REST/WebSocket APIs.
  • OpenAlgo remains responsible for authenticated market-data access.
  • AJ dashboard/debug panels should not expose credentials or tokens.
  • Worker messages should contain market/indicator state only.
  • Persistent settings should be validated before reaching the engine.
  • Use explicit package versions so a broker deployment cannot silently load an incompatible AJ engine.

21. Implementation roadmap

Milestone 1

Architecture extraction

Define contracts, package boundaries and import graph. Keep current implementation intact.

Milestone 2

Core + adapter

Move AJ logic into Core and build the generic OpenAlgo adapter/orchestrator.

Milestone 3

Performance

Incremental engine, caching and Web Worker execution.

Milestone 4

UI integration

Dashboard, debug, advisory and zone panels consume shared state.

Milestone 5

Second broker

Install unchanged AJ packages into IndStocks OpenAlgo and run golden tests.

Milestone 6

Reusable platform

Freeze the AJ/OpenAlgo base and add future indicators through manifests/catalog entries.

Recommended implementation order

  1. Do not start by rewriting the UI.
  2. Do not start by optimizing individual AJ calculations.
  3. First isolate the calculation core and define the contracts.
  4. Then build the generic adapter/orchestrator.
  5. Then prove identical output against the current working implementation.
  6. Then move the calculation into a worker and optimize incremental updates.
  7. Finally migrate dashboard/debug/advisory components.

22. Final architecture decisions

#DecisionRecommendation
1AJ source ownershipSingle shared AJ Core package.
2Broker integrationOpenAlgo owns broker connectivity; AJ consumes normalized bars.
3OpenAlgo integrationOne generic AJ OpenAlgo adapter/orchestrator.
4RegistrationKeep a thin registration boundary because OpenAlgo requires registration; remove business logic from it.
5VisualizationOpenAlgo Charts is the renderer; AJ supplies descriptors/results.
6Dashboard/debug/advisoryReact UI consumers of shared AJ state.
7PerformanceIncremental calculation + cache + Web Worker for expensive computation.
8Multi-instanceSame AJ packages installed into every OpenAlgo broker instance.
9New brokerNo AJ source modification.
10New indicatorAdd indicator package/manifest; reuse the same orchestrator.
11Original applicationDo not copy the full AJMultiAlgo frontend/backend.
12ValidationGolden candle/result tests prove broker independence.

Final recommendation in one sentence

Build AJInstitutional as a broker-neutral calculation SDK, connect it to OpenAlgo through one reusable adapter/orchestrator and thin registration bridge, let OpenAlgo Charts own rendering, and deploy the same versioned packages into every broker-specific OpenAlgo instance.
